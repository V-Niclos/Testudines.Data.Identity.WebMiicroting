# Install ASP.NET Core Identity with MySQL or MariaDB (.NET 10)

*updated 2026-11-22*

This guide explains how to create a Blazor Web App that uses ASP.NET Core Identity with a MySQL or MariaDB database through the Microting Entity Framework Core provider. It covers database setup, migrations, development test accounts, and role-based authorization.

> **Version compatibility:** The example versions below follow the project details provided for this guide. Before installing them, confirm that the selected `Microting.EntityFrameworkCore.MySql` version supports .NET 10 and the EF Core version you choose. Keep `Microsoft.EntityFrameworkCore`, `.Design`, `.Tools`, `Microsoft.AspNetCore.Identity.EntityFrameworkCore`, and `dotnet-ef` on compatible versions. The .NET SDK version is independent of the EF Core package version.

## 1. Requirements

- Windows 11, optionally with WSL
- Visual Studio 2026 and the .NET 10 SDK
- A reachable MySQL or MariaDB server
- A new Blazor Web App project
- A Microting MySQL provider version compatible with the selected EF Core release

Use either Visual Studio's Package Manager Console or a terminal consistently. Commands below indicate the intended shell.

## 2. Create the Blazor Web App

In Visual Studio, create a **Blazor Web App** with these settings:

- Framework: **.NET 10.0**
- Interactive render mode: **Server**
- Interactivity location: **Global**
- Authentication type: **Individual Accounts**

Create the project. The template generates the Identity UI and application database context. Replace sample namespaces and project-specific type names in this guide with those generated by your project.

## 3. Install NuGet packages

The template may add the SQL Server provider. Remove it if present.

In **Package Manager Console**:

```powershell
Uninstall-Package Microsoft.EntityFrameworkCore.SqlServer
```

Or from a terminal in the application project directory:

```powershell
dotnet remove package Microsoft.EntityFrameworkCore.SqlServer
```

Install compatible packages. `10.0.14` is an example EF Core patch version; use versions confirmed to work together with the Microting provider:

```powershell
dotnet add package Microsoft.EntityFrameworkCore --version 10.0.14
dotnet add package Microsoft.EntityFrameworkCore.Design --version 10.0.14
dotnet add package Microsoft.EntityFrameworkCore.Tools --version 10.0.14
dotnet add package Microsoft.AspNetCore.Identity.EntityFrameworkCore --version 10.0.14
dotnet add package Microting.EntityFrameworkCore.MySql --version 10.0.14
```

Check existing package references before adding them again. Do not mix EF Core patch versions (for example, EF Core packages at `10.0.14` and Identity EF Core at `10.0.15`) unless the provider documentation confirms that combination is supported.

### 3.1 Check and pin the .NET SDK (optional)

List installed SDKs:

```bash
dotnet --list-sdks
```

Confirm that a .NET 10 SDK is installed. To pin the SDK for the solution, run this from the solution directory and substitute an SDK version present on your machine:

```bash
dotnet new globaljson --sdk-version 10.0.404 --roll-forward latestFeature
```

`10.0.404` is an example SDK version. `global.json` controls SDK selection; it does not set the EF Core package version. `latestFeature` follows the .NET SDK roll-forward rules. Verify the generated `global.json` and ensure the selected SDK is installed.

### 3.2 Install the EF Core CLI tool (optional)

The SDK and `dotnet-ef` are separate. Install `dotnet-ef` using a version compatible with the EF Core packages above:

```bash
dotnet tool install --global dotnet-ef --version 10.0.14
```

If it is already installed, use `dotnet tool update --global dotnet-ef --version 10.0.14`. Check the result with:

```bash
dotnet ef --version
```

For WSL/Linux, install the .NET SDK using Microsoft's instructions for your distribution, then install `dotnet-ef` with the command above. The `dotnet-install.sh` script installs the SDK, not the EF Core CLI tool.

## 4. Configure the connection string

For local development, set `IdentityConnection` in `appsettings.json` and replace the example values: Database

```json
{
  "ConnectionStrings": {
    "IdentityConnection": "Server=yout_database;Port=3306;Database=your_database;User=your_user;Password=your_passwords;"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*"
}
```

Create the database and a database user with only the permissions the application needs, unless your server/provider setup creates them. Do not commit real credentials. Use .NET User Secrets or environment variables locally, and a managed secret store in production.

## 5. Configure `Program.cs`

Replace the template's SQL Server database registration with the MySQL registration documented by the Microting provider. The sample below shows the intended structure. **Verify the `UseMySql` extension method, namespace, overload, and server-version argument against the exact Microting package version you install.** Provider APIs can differ.

```csharp
using Microsoft.AspNetCore.Components.Authorization;
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;
using YourApp.Components;
using YourApp.Components.Account;
using YourApp.Data;
using Microting.Web.Data.Seeders;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRazorComponents()
    .AddInteractiveServerComponents();

builder.Services.AddCascadingAuthenticationState();
builder.Services.AddScoped<IdentityRedirectManager>();
builder.Services.AddScoped<AuthenticationStateProvider,
    IdentityRevalidatingAuthenticationStateProvider>();

builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = IdentityConstants.ApplicationScheme;
    options.DefaultSignInScheme = IdentityConstants.ExternalScheme;
})
.AddIdentityCookies();

var connectionString = builder.Configuration.GetConnectionString("IdentityConnection")
    ?? throw new InvalidOperationException(
        "Connection string 'IdentityConnection' was not found.");

builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseMySql(connectionString, ServerVersion.AutoDetect(connectionString)));

builder.Services.AddDatabaseDeveloperPageExceptionFilter();

// Development/testing settings only. Choose a suitable policy before deployment.
builder.Services.AddIdentityCore<ApplicationUser>(options =>
{
    options.SignIn.RequireConfirmedAccount = false;
    options.Password.RequiredLength = 8;
    options.Password.RequireUppercase = false;
    options.Password.RequireLowercase = true;
    options.Password.RequireDigit = false;
    options.Password.RequireNonAlphanumeric = false;
    options.Password.RequiredUniqueChars = 1;
})
.AddRoles<IdentityRole>()
.AddEntityFrameworkStores<ApplicationDbContext>()
.AddSignInManager()
.AddDefaultTokenProviders();

builder.Services.AddSingleton<IEmailSender<ApplicationUser>, IdentityNoOpEmailSender>();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    using var scope = app.Services.CreateScope();
    await DbSeeder.InitializeAsync(scope.ServiceProvider);
}

if (app.Environment.IsDevelopment())
{
    app.UseMigrationsEndPoint();
}
else
{
    app.UseExceptionHandler("/Error", createScopeForErrors: true);
    app.UseHsts();
}

app.UseStatusCodePagesWithReExecute("/not-found", createScopeForStatusCodePages: true);
app.UseHttpsRedirection();
app.UseAntiforgery();
app.MapStaticAssets();
app.MapRazorComponents<App>()
    .AddInteractiveServerRenderMode();
app.MapAdditionalIdentityEndpoints();
app.Run();
```

Keep any other service registrations required by your generated template. Replace sample namespaces and types with the ones in your project. `RequireConfirmedAccount = false` allows sign-in without email confirmation. The no-op email sender is for development only.

## 6. Create and apply the Identity migration

## 7. Seed development test roles and users

Create `Data/Seeders/DbSeeder.cs` (or a folder that matches your project structure). Update the namespace and `ApplicationUser` type as needed. The seeder is called only in Development because the `Program.cs` call is guarded by `IsDevelopment()`.

```csharp
using Microsoft.AspNetCore.Identity;
using YourApp.Data;

namespace Microting.Web.Data.Seeders;

public static class DbSeeder
{
    public static async Task InitializeAsync(IServiceProvider services)
    {
        var roleManager = services.GetRequiredService<RoleManager<IdentityRole>>();
        var userManager = services.GetRequiredService<UserManager<ApplicationUser>>();

        string[] roles = ["admin", "editor", "translator", "user"];
        foreach (var role in roles)
        {
            if (!await roleManager.RoleExistsAsync(role))
            {
                var result = await roleManager.CreateAsync(new IdentityRole(role));
                EnsureSucceeded(result, $"creating role '{role}'");
            }
        }

        var users = new (string Email, string Password, string Role)[]
        {
            ("admin@test.local", "DevOnly-Admin-123", "admin"),
            ("editor@test.local", "DevOnly-Editor-123", "editor"),
            ("translator@test.local", "DevOnly-Translator-123", "translator"),
            ("user@test.local", "DevOnly-User-123", "user")
        };

        foreach (var item in users)
        {
            var user = await userManager.FindByEmailAsync(item.Email);
            if (user is null)
            {
                user = new ApplicationUser
                {
                    UserName = item.Email,
                    Email = item.Email,
                    EmailConfirmed = true
                };

                var createResult = await userManager.CreateAsync(user, item.Password);
                EnsureSucceeded(createResult, $"creating user '{item.Email}'");
            }

            if (!await userManager.IsInRoleAsync(user, item.Role))
            {
                var roleResult = await userManager.AddToRoleAsync(user, item.Role);
                EnsureSucceeded(roleResult, $"assigning role '{item.Role}' to '{item.Email}'");
            }
        }
    }

    private static void EnsureSucceeded(IdentityResult result, string operation)
    {
        if (!result.Succeeded)
        {
            var errors = string.Join("; ", result.Errors.Select(e => e.Description));
            throw new InvalidOperationException($"Identity failed while {operation}: {errors}");
        }
    }
}
```

These credentials are development-only examples. Never deploy the seeded accounts to production. The seeder does not change an existing user's password; update or delete that user explicitly if you change the sample credentials.

## 8. Test authentication and role-based UI

Create `Components/Pages/AuthTest.razor`:

```razor
@page "/auth-test"
@using Microsoft.AspNetCore.Components.Authorization

<h3>Authentication and role authorization test</h3>

<AuthorizeView>
    <Authorized>
        <div class="alert alert-success">
            Welcome, <strong>@context.User.Identity?.Name</strong>. You are signed in.
        </div>

        <AuthorizeView Roles="admin" Context="adminContext">
            <div class="alert alert-danger"><strong>Admin panel:</strong> visible to users in the admin role.</div>
        </AuthorizeView>

        <AuthorizeView Roles="admin,editor" Context="editorContext">
            <div class="alert alert-warning"><strong>Editor tools:</strong> visible to users in the admin or editor role.</div>
        </AuthorizeView>

        <AuthorizeView Roles="translator" Context="translatorContext">
            <div class="alert alert-info"><strong>Translator workspace:</strong> visible to users in the translator role.</div>
        </AuthorizeView>
    </Authorized>
    <NotAuthorized>
        <div class="alert alert-secondary">
            You are not signed in. <a href="/Account/Login">Sign in</a> with a development test account.
        </div>
    </NotAuthorized>
</AuthorizeView>
```

Nested `AuthorizeView` components use distinct `Context` names to avoid Razor context-name collisions.

For page-level authorization, create `Components/Pages/AdminOnly.razor`:

```razor
@page "/admin-only"
@using Microsoft.AspNetCore.Authorization
@attribute [Authorize(Roles = "admin")]

<h3>Restricted admin page</h3>
<p>Only users in the admin role can access this page.</p>
```

Ensure that authorization services and cascading authentication state are configured as required by your template. `AuthorizeView` controls presentation; protect server-side operations and endpoints with authorization checks as well.

### Verification checklist

1. Run the app in Development and confirm that Identity tables exist and seed data is present.
2. While signed out, open `/auth-test`; confirm that the sign-in link appears.
3. Sign in as `admin@test.local` with `DevOnly-Admin-123`; confirm that the Admin panel and Editor tools appear.
4. Sign out, then sign in as `translator@test.local` with `DevOnly-Translator-123`; confirm that only the Translator workspace appears.
5. While signed in as the translator, open `/admin-only`; confirm that access is denied or redirected to the configured access-denied flow.
6. Register a separate test account through the generated registration page. Sign out and sign in again to verify registration and login.
7. Test account deletion using the account-management flow generated by your template. The Personal Data page may provide export and deletion flows; verify its actual behavior instead of assuming it is a generic delete-user page.
8. If a step fails, inspect application logs and the seeder's `IdentityResult` errors.

## 9. Production hardening

Before deployment:

- Require confirmed accounts if your product needs email verification, and configure a real email sender for confirmation and password-reset messages.
- Choose a password and lockout policy appropriate to your application. The values below are examples, not a universal security guarantee.
- Keep test seeding restricted to Development and remove test accounts/data from production databases.
- Store credentials in environment variables, .NET User Secrets for local development, or a managed secret store. Do not commit real secrets.
- Use HTTPS, secure database access, backups, least-privilege database credentials, and a reviewed migration/deployment process.
- Protect sensitive server operations with authorization checks. Hiding UI elements alone is not access control.

Example policy settings (adjust to your requirements):

```csharp
options.SignIn.RequireConfirmedAccount = true;
options.Password.RequiredLength = 12;
options.Password.RequireUppercase = true;
options.Password.RequireLowercase = true;
options.Password.RequireDigit = true;
options.Password.RequireNonAlphanumeric = false;
options.Password.RequiredUniqueChars = 1;
options.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15);
options.Lockout.MaxFailedAccessAttempts = 5;
options.Lockout.AllowedForNewUsers = true;
```

Apply these settings inside the existing `AddIdentityCore<ApplicationUser>(options => { ... })` block; do not add a second Identity registration.
